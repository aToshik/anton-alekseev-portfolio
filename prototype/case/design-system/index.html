Work/Design System for AI Agents

Design System · AI · B2B  |  MarketingOS, Kissterra · sole product designer · 56 components · ~1,050 tokens

How I made a design system AI agents can build from

15 → 2 · design questions per feature Minutes, not hours · Figma → repo sync

Figma · Claude Code skills · Figma MCP · DTCG tokens · consumed by Cursor & Claude Code

My role

Sole designer and owner of the system. I diagnosed the problem, designed the documentation format, and built the AI workflow that keeps Figma and the repo in sync.

Context

Engineers started shipping with AI agents

MarketingOS is Kissterra's dense B2B analytics and campaign platform. I built its design system as the sole product designer. Then the frontend team moved to AI-assisted development: Cursor and Claude Code implemented features straight from Figma and specs. Our engineers started shipping features with AI coding agents, and those agents read my design system literally.

The system

56 components, every state accounted for

The library covers the full range of a data-dense product: from atomic controls (Button, Checkbox, Switch, Input) to complex composites (Analytics Table, Mega Chart, Date Range Selector, the filter system). Every component is specified across each size, style and state, and every value is mapped to a token.

Primitives~280

color, spacing, radius, type

Semantic~150

surfaces, interactive states, status

Components~620

per-component properties

Three collections in the DTCG format, with every alias chain resolved in the docs, from component token to semantic to primitive to the final value. System intent stays visible instead of hiding behind raw hex.

Problem

Design became the bottleneck of a pipeline built to be fast

The system was written for humans. An experienced developer fills gaps from context: what a table shows while loading, what closes a dropdown, who owns the empty-state copy. An agent reads the spec literally and fills every gap with a plausible guess. The result looked almost right, and "almost right" is the expensive kind of wrong. Every guess turned into a question for me, and the feature stopped until I answered.

The system drifted. Figma kept changing (renamed tokens, new props), the docs didn't. A stale token name in a spec becomes a wrong CSS variable in generated code, silently.

Insight

Tokens said how it looks. Nothing said how it behaves.

The questions weren't about missing details. They were about missing categories of information. After the Analytics Table shipped, developers came back with 15 questions. I sorted them:

8behavior edge cases 2consumer vs component 2accessibility strings 3tokens, sizes, spec authority

None of these had a place in the doc template. Careful writing couldn't fix it. The template had to change, and something had to keep it true as Figma moved.

Key decisions

Documentation as an interface for a new kind of user

01Two contracts 02Doc format v1.1 03Name every diff 04Generated vs curated
01 · One component, two contracts

Each component got a compact, structured description in Figma, written for agents to parse (anatomy, props, tokens, a11y in a fixed syntax), and a full Markdown spec in the code repo for developers. Figma's "Link to documentation" points straight to the repo doc. Rejected: one long doc for everyone. Agents lose precision in prose; developers lose context in a terse contract.

02 · A doc format driven by real failures

Every question category became a section. States: entry condition and visual for loading, error, empty. Behavior: a dismiss matrix for overlays (×, Escape, click outside, CTA, timer). Consumer contract: what the component owns vs what the developer must provide.

03 · Every difference gets a name

The goal was never zero drift; Figma is supposed to change. The goal was that no change goes unnoticed or unnamed. Every difference is classified by risk before anything is written. Critical: a token or prop removed or renamed. High: a value changed. Low: something new added. Nothing is applied without my approval. Rejected: fully automatic sync. A rename can break code; a person should see it first.

04 · Generated vs curated sections

Props and token mappings are regenerated from Figma. Purpose and implementation rules are written by hand and never overwritten. Automation keeps facts fresh without erasing judgment.

AI workflow

Agents keep it current. Agents build from it.

The system runs as two loops. In the first, agents keep Figma and the repo in sync, and I approve every change: component docs, Figma descriptions and the token files in the repo update together. In the second, coding agents build from two layers of documentation (the compact spec in each Figma component's description and the full .md doc in the repo) and from tokens that always match Figma. Whatever they still can't answer improves the format.

Reads every token and component prop from Figma through the Figma MCP, compares them with the last approved baseline and writes a risk-rated drift report.

Runs the audit, shows me the report and waits for my approval. One command for the whole cycle.

ds:update

Applies what I approved: the token files in the repo, the affected doc sections, and the compact description on each Figma component. Developers always have the current token set at hand.

An agent that interviews the designer. When a component doc is created or updated, the agent runs the v1.1 checklist. For every missing section it asks me targeted questions in a fixed order: behavior, then states, then accessibility strings, then the consumer contract. I answer; it writes and validates the section. Docs get complete without me starting from a blank page.

Coding agents built from complete, current specs and from tokens that always match Figma, instead of guessing. Audits caught a table restructure with 7 breaking token renames before it reached an engineer.

Reflection

Agents are the fastest way to find ambiguity in a design system. Every gap they hit was a decision we had never written down.

A component spec is no longer something a human might read someday. It's a contract parsed at implementation time. Documentation quality turned out to be a structural problem, not a writing problem, and that is a design problem. Next: a pattern layer above components (how a settings page or a filter bar is composed, not just which parts it uses), scheduled weekly audits, links to Storybook stories.
